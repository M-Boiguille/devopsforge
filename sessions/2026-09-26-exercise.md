# Exercice DevOps — « LogScope » : pipeline d'analyse de logs en Bash robuste

**Durée cible : 45 min** (30 min si tu connais déjà `getopts`, 60 min si tu veux faire le bonus)
**Projet fil rouge : `logscope`** — une CLI d'analyse de logs d'API qui deviendra plus tard un conteneur Docker, puis un job Kubernetes. Rien n'est encore industriel : **cet incrément 0 pose les fondations Bash + parsing sur lequel tout le reste s'appuiera.**

---

## Contexte

Ton équipe reçoit des logs d'API au format *JSON Lines* (un objet JSON par ligne). Personne n'a le temps de les lire à la main et les scripts jetables se cassent dès qu'un champ est manquant. Tu vas écrire **`logscope.sh`**, un script idempotent, testable et *shellcheck-clean*, capable de répondre à une question métier : *« Quels endpoints ont le plus d'erreurs, et en combien de temps ? »*.

## Instructions

### 0. Lecture préalable (5 min, 20 % du temps)

Parcours ces deux ressources avant de coder :
- 🧾 **ShellCheck — liste des warnings** : https://www.shellcheck.net/wiki/
- 📘 **BashFAQ / Wiki Greg's** (pipes & subshells, quoting) : https://mywiki.wooledge.org/BashFAQ/024

Objectif : savoir *pourquoi* `while read` dans un pipe perd ses variables (indice : subshell).

---

### 1. Préparer un jeu de données (3 min)

Crée `access.log` avec au moins **12 lignes** JSON, dont :
- 3 lignes valides,
- 2 lignes avec `"status":500`,
- 1 ligne volontairement **malformée** (JSON tronqué),
- 1 ligne sans le champ `latency_ms`.

Exemple :
```jsonl
{"ts":"2024-05-01T10:00:01Z","level":"INFO","path":"/api/users","status":200,"latency_ms":12}
{"ts":"2024-05-01T10:00:02Z","level":"ERROR","path":"/api/orders","status":500,"latency_ms":430}
{"ts":"2024-05-01T10:00:03Z","level":"INFO","path":"/api/orders","status":200,"latency_ms":88}
```

---

### 2. Squelette du script (8 min)

Crée `logscope.sh` avec **impérativement** :

1. Shebang `#!/usr/bin/env bash`
2. `set -euo pipefail` en tête
3. Une fonction `usage()` et une fonction `log_error()` (vers `stderr`, préfixée `[ERROR]`)
4. **`getopts`** supportant au minimum :
   - `-i <file>` : chemin du fichier de log (**obligatoire**)
   - `-l <level>` : filtre par `level` (défaut `ERROR`)
   - `-n <int>` : nombre de résultats (défaut `5`)
   - `-h` : aide
5. Vérifie l'existence du fichier **et** que `jq` est installé, sinon message clair + `exit 1`
6. Un `trap` sur `EXIT` affichant un récap (`[INFO] terminé en N commandes` via `${SECONDS}`)

> 🎯 Piège classique : l'opérateur `${var:-default}` vs `${var:=default}`. Utilise le bon.

---

### 3. Le cœur : parsing + agrégation (15 min)

Ajoute une fonction `report()` qui :

1. Filtre les lignes **valides** (rejette les malformées avec `jq -e .` ou `grep -E '^\{.*\}$'`).
2. Filtre sur `level == $LEVEL_FILTER` (via `jq -r 'select(.level==...)'`).
3. Agrège par `path` : compte + latence moyenne, en utilisant :
   - `awk` **ou** `jq -s 'group_by(.path) | …'` (au choix, mais justifie en commentaire),
   - puis `sort | uniq -c | sort -rn` **ou** l'équivalent jq.
4. Affiche un tableau aligné : `count | path | avg_latency_ms`, limité aux `N` premiers.
5. Redirige les rejets vers `stderr` avec un compteur : `[WARN] 2 lignes ignorées (JSON invalide)`.

Contrainte forte : **aucun `cat | grep`**, pas de `awk` pour faire le travail de `jq`, pas de `grep` pour faire le travail d'`awk`.

---

### 4. Robustesse & lint (7 min)

1. `shellcheck logscope.sh` → **zéro warning** (justifie par `# shellcheck disable=` seulement si réellement nécessaire, avec commentaire).
2. Teste ces cas et corrige si besoin :
   - `./logscope.sh` sans `-i` → `usage` + `exit 1`
   - fichier inexistant → erreur claire
   - `-n abc` → erreur de validation (utilise `[[ "$N" =~ ^[0-9]+$ ]]`)
   - log vide → sortie vide mais `exit 0`
3. Vérifie qu'une erreur au milieu (ex : `jq` absent) **stoppe** le script (`set -e`).

---

### 5. Bonus (optionnel, +5 min)

Ajoute `-o json` qui sort le rapport en JSON *propre* via `jq -n`, sans réécrire le pipeline (`case "$FORMAT" in`).

## Grille de notation (pondérée)

Exercice de type **scripting / parsing** → la robustesse et le design pèsent autant que la fonctionnalité brute.

| Dimension | Poids | Ce qui est évalué |
|---|---|---|
| **Implémentation** | 30 % | Le script produit un rapport correct sur le jeu de données fourni |
| **Design** | 20 % | Fonctions courtes et nommées, séparation parsing / rendu, `getopts` propre |
| **Debug / robustesse** | 20 % | `set -euo pipefail`, `trap`, gestion des cas limites (JSON malformé, options invalides) |
| **Sécurité** | 10 % | Quoting systématique (`"$var"`), pas d'`eval`, pas de `rm` non validé, validation d'entrées |
| **Performance / élégance** | 10 % | Un seul passage par fichier quand possible, pas de fork inutile (`$(cat …)`), awk/jq utilisés pour ce qu'ils font bien |
| **Explication** | 10 % | Commentaires justifiant un choix (`awk` vs `jq`, subshell évité) + `shellcheck` clean prouvé |

**Seuil de validation : 70 %.** Un `shellcheck` non-clean plafonne automatiquement *Debug* à 50 %.

## Critères de réussite

✅ `shellcheck logscope.sh` sort **sans aucun warning**.
✅ `./logscope.sh -i access.log` affiche les top 5 endpoints en erreur, triés par count décroissant.
✅ `./logscope.sh -h` affiche l'aide et sort en `0`.
✅ `./logscope.sh` sans argument affiche l'usage sur `stderr` et sort en `1`.
✅ Les lignes JSON malformées sont **comptées et signalées** sans interrompre le script.
✅ Tu peux **expliquer** en une phrase pourquoi tu as évité `while read | ...` ou pourquoi tu ne l'as pas évité.
✅ Le script se relance deux fois de suite **sans effet de bord** (idempotence).

💡 **Message du formateur** : ce n'est pas la beauté du tableau en sortie qui compte, c'est le comportement *quand ça casse*. Un bon script Bash, c'est celui qu'on peut mettre dans un cron à 3 h du matin sans surveiller. Prends 5 minutes pour casser le tien volontairement (fichier vide, permission refusée, `jq` absent) : c'est là que tu apprends le plus. Quand tu as fini, garde le script : l'incrément 1 (Dockerisation) arrivera vite. 🚀
